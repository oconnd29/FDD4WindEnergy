## Stage 4 — Metric Selection

### Recommended metric set

- **Expected cost / net benefit** (operational; accepted; valid on current protocol)
  - Why: Cost / Impact Optimisation requires an expected cost or net-benefit model from declared terms.
  - Limitation: Requires explicit, usually site-specific, cost terms and a sensitivity check.
  - Gück et al., 2024; Kamariotis et al., 2024
- **Cost-weighted error** (operational; rejected; valid on current protocol)
  - Why: A cost-weighted error makes the same terms visible as a single loss.
  - Limitation: The weights are the evaluation. Report them.
- **False fault-detection rate** (case; accepted; valid on current protocol)
  - Why: False fault detections enter the cost model and should also be reported raw.
  - Limitation: Does not measure sensitivity to faulty cases.
- **Faulty-case detection rate** (case; accepted; valid on current protocol)
  - Why: Missed faulty cases enter the cost model and should also be reported raw.
  - Limitation: Does not show false fault detections in healthy cases.
- **Warning lead time** (earliness; accepted; valid on current protocol)
  - Why: Delay cost needs a defined detection point and reference event.
  - Limitation: Has no clear meaning unless both the detection point and reference event are stated.
- **Unified CARE score** (combined; accepted; valid on current protocol)
  - Why: Early Warning is a secondary objective, so report unified CARE with C, A, R and E.
  - Limitation: Additive aggregation allows compensation. Report C, A, R and E alongside the unified score. Weights must be stated.
  - Gück et al., 2024; OECD et al., 2008
- **CARE Coverage (C)** (instance; accepted; valid on current protocol)
  - Why: CARE Coverage remains the instance-level detection component on faulty cases.
  - Limitation: Does not by itself measure healthy-case stability or case-level decisions.
  - Gück et al., 2024
- **CARE Accuracy (A)** (instance; accepted; valid on current protocol)
  - Why: CARE Accuracy remains the healthy-case instance summary.
  - Limitation: Does not establish that anomalies persist enough to detect a faulty case.
  - Gück et al., 2024
- **CARE Reliability (R)** (case; accepted; valid on current protocol)
  - Why: CARE Reliability remains the case-level fault-detection component.
  - Limitation: Depends on the selected persistence or fault-detection condition.
  - Gück et al., 2024
- **CARE Earliness (E)** (earliness; accepted; valid on current protocol)
  - Why: CARE Earliness remains the timing component inside the event window.
  - Limitation: Requires a defined event window; does not by itself establish a fault detection.
  - Gück et al., 2024
